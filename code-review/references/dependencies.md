# Dependencies

Read when the change adds, removes or upgrades a dependency, or touches a lockfile.

## A new dependency

- Does the standard library or a dependency the project already has do this? Why: every dependency is code you ship and must keep updated.
- Who maintains it, when was its last release, and how many open issues does it have? A package released days ago, or one renamed from a popular one by a single letter, needs a closer look. Why: these are common ways malicious packages get in.
- What does it pull in transitively, and how large is it?
- Is its license compatible with the project?

## An upgrade

- Read the changelog between the old and new versions, not just the version number. Why: a minor or patch release can still change behaviour.
- For a major version, read the migration notes and find what breaks.
- One dependency per change. Why: when a bulk upgrade breaks the build, you can't tell which package did it, and you can't revert just one.
- The tests pass before and after. If the tests barely touch what the dependency does, that gap is the finding.

## The lockfile

- Review the lockfile diff, not only the manifest. Why: one direct upgrade can change dozens of indirect packages.
- The lockfile is committed and generated by the tool, never edited by hand. A project should have exactly one lockfile.

## Run the audit

Run the project's own audit and report the result, for example `npm audit`, `pnpm audit`, `pip-audit`, `govulncheck ./...` or `cargo audit`. An audit only knows published advisories; it won't catch a newly malicious package.

Installing packages runs their install scripts. In a PR from a fork or from outside the team, install only in the copy, and only after the user has said yes (see [reviewer-brief.md](reviewer-brief.md)).
